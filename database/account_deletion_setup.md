# Account deletion workflow

Apply `mysql_account_deletion.sql` to the intended database **before deploying the new code**. Choose the schema explicitly (`USE defaultdb;` for Aiven). This migration adds two tables; it does not modify users or approve/delete requests. No SQL was applied remotely during development.

Settings links to `/AccountDeletion`. Existing account-menu Log out remains available. Staff accounts cannot request self-service deletion. A verified email and current password are required to send a confirmation code; the code expires after ten minutes, permits five attempts, has a 60-second resend cooldown and a five-send/15-minute window. Codes are hashed and bound to the account password version. A verification-only draft does not block work. Confirming the code starts the 72-hour clock and the pending request.

Pending, held and approved requests block new task publication, offers and booking/offer acceptance. Existing work, cancellation, messages and completion remain available. Cancelling an active request immediately removes this restriction. A new request after cancellation requires password/email verification and a new waiting period. A held/rejected request can be resubmitted for review without losing its original waiting period; the original request must already have been email-confirmed.

`/AdminDeletions` requires the AdminOnly policy. It is linked in Admin navigation. Decisions require a reason and a manual evidence-review attestation; reviewers cannot review themselves. Approval is refused when automatic blockers are found. Admins must inspect free-text safety targets and documented obligations manually: there is no payment/debt ledger that can certify all debts. Resolved past offenses and poor ratings alone are not automatic blockers.

The background worker checks every five minutes while the service is running. It never finalizes before 72 hours and requires approved status and a recorded reviewer. It rechecks the reviewer's role, unfinished owned/accepted work, pending bookings/offers and linked unresolved safety/legacy cases inside a serializable transaction. If blockers appear it records On hold and requires another review. Cancellation, review and finalization serialize on the user row. Free hosting sleep can delay finalization; the timestamp is the earliest eligible time, not a delivery guarantee.

Finalization is **account anonymization**, preserving the surrogate user ID and work/conversation/report history for other participants and accountability. It clears the name/email/password/birthday/profile photo, removes the freelancer profile, precise freelancer coordinate history, ID/resource blobs and ID suffix/review note, revokes sessions/trust/challenges, and removes registration/reset/email verification records. Historical messages, work addresses, safety evidence, admin reasons and other participants' records are retained; this is not a claim that every mention of a person in historical free text or backups is erased. Staff must avoid including unnecessary personal data in retained reasons. A broader retention/backup-erasure policy remains separate.

Email updates are best-effort after transactions commit; mail failure does not undo a confirmed request, cancellation or review. Pending status, blockers and decision history remain visible in-app. Final completion and automatic holds also attempt an email. No financial settlement, automated judgment of guilt, instant irreversible user-row delete, or removal of safety history occurs.

Validation during development uses synthetic policy/model/page tests only; no production account was created, approved, cancelled, anonymized or deleted for testing. End-to-end MySQL transaction/concurrency and SMTP delivery should be exercised with disposable accounts in a separate test database before approving real requests.
